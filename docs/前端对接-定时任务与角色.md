# 前端对接：教师/导师角色与定时同步管理

> 适用版本：2026-11 起 ｜ 相关接口：`/auth/profile`、`/mentor-applications/*`、`/sync/*`

## 1. 角色模型变了

以前同步来的教师直接绑 `mentor` 角色，导致「所有教师都是导师」。现在拆成两个角色：

| 角色 | 谁有 | 能做什么 |
| --- | --- | --- |
| `teacher` | 所有从 SSO 同步来的教师 | 提交/撤回入驻申请、维护本人档案、检索导师、上传材料、看自己的消息 |
| `mentor` | **入驻审核通过后**才追加 | 在 `teacher` 之上，增加时段管理、处理预约、查看评价/考核/归档/成果等导师能力 |
| `student` | 学生 | 检索导师、发起预约、写评价、看自己的消息/成果 |
| `college_admin` / `sc_admin` | 管理员 | 审核、统计、配置等管理能力 |

关键点：

- `teacher` 是**身份**，`mentor` 是**审核通过后的能力**。
- 审核通过时后端会在同一个事务里给账号追加 `mentor` 角色，并清掉权限缓存；前端重新拉一次 `GET /auth/profile` 就能拿到新增的权限码。
- 「是不是真正的导师」不要看角色，看导师档案：
  - `GET /mentor/profile` 返回的 `status`：`2 = 已生效`；
  - `GET /mentors` 只返回已生效档案，未审核通过的教师不会出现在导师列表里。

### 前端怎么判断

登录后调 `GET /auth/profile`：

```json
{
  "user": { "username": "20250001", "authSource": "sso", "roleIds": ["..."] },
  "permissions": ["mentor:profile", "mentor-application:submit", "..."],
  "menus": [...]
}
```

- 有 `mentor-application:submit` → 显示「申请成为导师」入口。
- 有 `mentor:slot-manage` / `appointment:handle` → 显示导师工作台（说明已审核通过）。
- 不要用「有没有 `mentor` 角色」做前端判断；`/auth/profile` 只返回 `roleIds`，角色 code 需要另外查，权限码才是稳定的契约。

### 审核通过后

1. 申请人重新调 `GET /auth/profile` 拿新权限码；
2. 如果前端缓存了菜单/按钮，按新 `permissions` 重算；
3. 导师档案 `status` 变为 `2`，`GET /mentor/profile` 可读。

## 2. 定时同步管理

### 2.1 查看当前设置

```http
GET /sync/schedule
Authorization: Bearer <accessToken>
```

需要权限码：`sync:manage`（超管默认绕过；已绑给 `sc_admin`）。

响应：

```json
{
  "code": 0,
  "data": {
    "enabled": true,
    "intervalSeconds": 21600,
    "fullIntervalSeconds": 604800,
    "studentsEnabled": false,
    "running": false,
    "nextRunAt": "2026-11-05T12:30:00.000Z",
    "lastRun": {
      "id": "5",
      "source": "sso",
      "mode": "incremental",
      "status": 1,
      "startedAt": "2026-11-05T06:13:39.968Z",
      "finishedAt": "2026-11-05T06:13:42.975Z",
      "total": 202,
      "okCount": 202,
      "failCount": 0
    }
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `enabled` | 是否启用定时同步 |
| `intervalSeconds` | 触发间隔（秒） |
| `fullIntervalSeconds` | 全量同步间隔（秒） |
| `studentsEnabled` | 是否同步学生；缺 `edu:classes` 能力键时保持 `false` |
| `running` | 当前是否有同步在跑 |
| `nextRunAt` | 下次触发时间（UTC ISO 8601）；关闭时为 `null` |
| `lastRun` | 最近一条流水；从未跑过为 `null` |

### 2.2 修改设置

```http
PUT /sync/schedule
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "enabled": true,
  "intervalSeconds": 3600,
  "fullIntervalSeconds": 604800,
  "studentsEnabled": false
}
```

- 只传要改的字段，没传的保持原值。
- `intervalSeconds` 最小 60；`fullIntervalSeconds` 最小 3600。
- 写入数据库 `SysConfig` 后立即重新排期；多实例下其他副本 60 秒内回读生效。
- 返回结构与 `GET /sync/schedule` 相同。

### 2.3 立即执行

```http
POST /sync/sso/run
Authorization: Bearer <accessToken>
Content-Type: application/json

{ "mode": "incremental" }   // 或 "full"
```

需要权限码：`sync:run`。

- 返回 `202` + `{ "runId": "42" }`，同步在后台执行；
- 已有同步在跑时返回 `409 / 10006`；
- 用 `GET /sync/runs?source=sso` 查状态。

### 2.4 查流水

```http
GET /sync/runs?source=sso&page=1&pageSize=10
Authorization: Bearer <accessToken>
```

`status`：`0 RUNNING / 1 OK / 2 PARTIAL / 3 FAILED`。
列表不返回失败明细 `detail`；需要排障时查库：

```sql
SELECT id, status, total, ok_count, fail_count, detail
FROM sync_run ORDER BY id DESC LIMIT 5;
```

## 3. 学生同步的前置条件

学生接口的 `organization` 是**班级名称**（如 `26专升本医学检验技术2班`），后端需要调 SSO 的
`/api/open/edu/classes` 把班级映射到学院，再映射到部门。

当前 SSO 应用缺少 `edu:classes`（以及 `edu:org`）能力键，所以：

- `studentsEnabled` 保持 `false`，定时同步只同步组织 + 教师；
- 学生在同步里被跳过，不会产生半成品账号；
- 等 SSO 管理员在「应用管理 → 开放接口能力」里勾上 `edu:classes` 后，把 `studentsEnabled` 改成 `true`，下一次同步就会导入学生并绑定 `student` 角色。

## 4. 现有数据回填说明

部署后执行一次 `npm run db:seed`（幂等），会做教师角色回填：

- 没有已生效导师档案的教师：摘掉 `mentor`，补 `teacher`；
- 已有生效档案的教师：保留/补 `mentor`，同时补 `teacher`；
- 外校导师（`externalMentor`）与管理员不受影响；
- 清理历史遗留的 `部门名（sso:xx）` 后缀：有同名部门的合并过去，没有的原地改名。
  同步不再创建带后缀的部门，登录与同步的用户落在同一个 `SysDept` 上；
- 合并重复根部门：历史 seed 可能建出第二个根（如「总部」）。以 admin 所在根为准，
  按「同名同父」合并子树，并把用户 / 同步组织 / 归档 / 学生成果的部门快照一并改挂，
  避免「计算机学院管理员看不到软件工程系预约」这类同院不同树的问题。

回填日志示例：

```
教师角色回填：teacher +1954，mentor +0，mentor -1954
```

## 5. 权限码速查

| 权限码 | 用途 | 绑定角色 |
| --- | --- | --- |
| `mentor:profile` / `mentor:profile-update` | 本人档案 | `teacher` / `mentor` |
| `mentor-application:submit` / `withdraw` / `list` | 入驻申请 | `teacher` / `mentor` |
| `mentor:search` | 检索导师 | `teacher` / `mentor` / `student` / 管理员 |
| `mentor:slot-manage` | 管理本人时段 | `mentor`（审核通过后） |
| `appointment:handle` / `appointment:list` | 处理/查看预约 | `mentor` / 管理员 |
| `sync:run` | 手动触发同步 | `sc_admin` / 超管 |
| `sync:manage` | 查看/修改定时同步设置 | `sc_admin` / 超管 |

## 6. 常见问题

| 现象 | 原因 |
| --- | --- |
| 教师登录后看不到「申请成为导师」 | 账号没有 `teacher` 角色或 `mentor-application:submit` 权限；检查同步是否成功、是否执行过回填 |
| 审核通过后导师工作台还是灰的 | 前端缓存了旧权限；重新拉 `GET /auth/profile` |
| 教师出现在导师列表里 | 导师列表只看 `MentorProfile.status=2`；如果出现，说明档案已生效，不是角色问题 |
| `PUT /sync/schedule` 返回 403 | 账号没有 `sync:manage`；用超管或 `sc_admin` |
| `POST /sync/sso/run` 返回 409 | 已有同步在跑；等 `GET /sync/schedule` 的 `running=false` 再试 |
| 同步成功但学生没进来 | `studentsEnabled=false` 或 SSO 缺 `edu:classes` |

## 7. 进程重启后的遗留状态

- 同步进程崩溃/重启时，可能留下 `status=0 RUNNING` 的流水和 `sso:sync:lock`。
- 下一次成功拿到锁的同步会把遗留的 RUNNING 流水标成 `3 FAILED`（`detail.reason=stale_running`）。
- 锁的 TTL 是 1 小时；崩溃后最多等 1 小时才会被下一次触发接管。
- 管理页看到 `running=false` 但 `lastRun.status=0` 时，说明这是上一个进程留下的；等下一次同步或手动触发即可清理。

## 8. 超级管理员角色（2026-11-10）

超级管理员采用**「角色 + 标志」双写**：

- 内置角色 `super_admin`（名称「超级管理员」，数据范围 `all`）出现在角色管理页；
- 用户持有该角色时，`SysUser.isSuperAdmin = true`；
- 摘除该角色时，标志同步为 `false`；
- 实际鉴权仍走 `isSuperAdmin`，所以新增权限点会**自动**被超管拥有，不需要逐个补角色授权。

### 前端操作

- 角色管理页：`super_admin` 标记为「内置」，**不显示停用 / 删除**按钮；
- 用户管理页：超级管理员可在他人行点「设为超管 / 取消超管」；
- 用户角色分配弹窗：可以勾选 `super_admin`，效果与「设为超管」一致；
- 建号弹窗：**不提供** `super_admin` 选项；需要先建号，再设置超管。

### 后端约束

| 操作 | 结果 |
| --- | --- |
| 非超管设置 / 取消他人超管 | 403 / 10003 |
| 非超管分配 / 摘除 `super_admin` 角色 | 403 / 10003 |
| 取消自己的超管身份 | 409 / 21105 |
| 删除 `super_admin` 角色 | 409 / 22103 |
| 修改 `super_admin` 的 code / dataScope / 停用 | 409 / 22103 |
| 建号时直接绑定 `super_admin` | 400 / 10001，提示先建号再设置 |

变更超管身份或角色后，目标账号的令牌会作废，需要重新登录。
