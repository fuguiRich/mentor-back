## 1. 需求全景

### 1.1 一句话

校内外创新创业导师的「入驻 → 预约 → 指导 → 评价 → 考核 → 归档」全周期管理。

### 1.2 四个角色 × 三条主线

| 角色 | 数据范围 | 主要动作 |
| --- | --- | --- |
| 学生 | 只看自己 | 检索导师、发起预约、传材料、确认记录、评价、导出个人档案 |
| 导师（校内 / 校外） | 只看自己 | 维护信息、管理时段、处理预约、填记录、传材料、看统计、申诉 |
| 二级学院管理员 | **本院** | 入驻审核、考核初评、对接监控、成果关联、本院报表 |
| 双创学院管理员 | **全校** | 数据修改、考核终评、全校统计、资源库统筹、归档、参数、互通、分析 |

三条业务主线：

1. **入驻审核**：填报 → 二级学院审 → 双创学院审 → 生效
2. **预约指导**：发起 → 确认 → 指导 → 记录 → 确认 → 评价
3. **考核归档**：初评 → 终评 → 归档（含申诉）

### 1.3 功能组清点

需求共 **34 个功能组**：学生端 6（§2.1–2.6）、导师端 8（§3.1–3.8）、共有 7（§4.1–4.7）、二级学院 5（§5.1–5.5）、双创学院 8（§6.1–6.8）。

## 2. 数据归属：同步 vs 本系统（本次决策的核心影响）

用户数据与组织架构**由外部接口定期同步**，本系统只留表。这把数据切成两层：

### 2.1 同步层（外部系统拥有，本系统只读落库）

| 表 | 内容 | 来源 |
| --- | --- | --- |
| `SyncOrgUnit` | 学院 / 系所树 | 组织架构接口 |
| `SyncPerson` | 学号·工号、姓名、人员类型（学生 / 校内导师 / 校外导师）、学院、专业、行政班级、电话 | 用户数据接口 |
| `SyncRun` | 每次同步的批次：时间、条数、成功 / 失败、失败明细 | 本系统生成 |

**本系统对同步层的义务**：
- 周期拉取、增量或全量落表；**源系统删除的行**要有明确处置（软删 / 标记离场）
- 同步失败**必须看得见**——`SyncRun` 记录失败明细，不能静默吞
- 同步层的表**不给业务写入口**，只有同步任务能写

### 2.2 业务层（本系统拥有）

| 表 | 归属流程 | 关键点 |
| --- | --- | --- |
| `MentorProfile` 导师专业档案 | 全部 | 指导方向、简介、研究成果、职称资质、合作单位、社会任职；状态：草稿 / 待审 / 通过 / 未通过 / 冻结 / 已移出 |
| `MentorApplication` 入驻·改信息申请 | 入驻流 | 两级审核各一跳 |
| `MentorMaterial` 导师佐证材料 | 入驻流 | 职称证书、行业资质 |
| `MentorTimeSlot` 可指导时段 | 预约流 | 周几 + 起止；开放 / 关闭 |
| `Appointment` 预约 | 预约流 | 5 类预约；状态见 §4.2 |
| `AppointmentMaterial` 预约材料 | 预约流 | 图片 / PDF，多份 |
| `GuidanceRecord` 指导记录 | 预约流 | 学生确认 / 异议 |
| `GuidanceMaterial` 过程材料 | 预约流 | 课件、笔记、修改意见 |
| `StudentReview` 学生评价 | 考核流 | 三维度评分 |
| `Assessment` 考核 | 考核流 | 初评 + 终评两跳 |
| `AssessmentAppeal` 考核申诉 | 考核流 | |
| `Achievement` 双创成果 | 考核流 | 竞赛获奖 / 项目立项 |
| `ArchiveItem` 归档 | 归档 | 保存期、清理规则 |
| `SysParam` 系统参数 | 平台 | 预约有效期、提交时限、考核权重 |
| `OpLog` 操作记录 | 平台 | §6.1 后台改数据留痕 |
| `FileObject` 文件对象 | 平台 | 本地存储：UUID 文件名 + 原名 + 类型 + 大小 + 上传人 |

### 2.3 两层怎么接

- 业务表通过 **`SyncPerson.id`**（或学号 / 工号）关联到人，**不冗余姓名学院**——显示时联查同步层
- 导师**专业档案**（指导方向、成果、资质）是业务层，挂在同步来的导师账号上
  → 所以 §6.4 的「批量导入校内外导师信息」**只剩专业档案的补录**，账号导入不需要了
- 数据权限（「二级学院管理员只看本院」）以 **`SyncOrgUnit`** 为准

### 2.4 对 general-back 复用范围的修正

| general-back 模块 | 原设想 | 现在 |
| --- | --- | --- |
| `user` | 直接复用 | **`SysUser` 成为 `SyncPerson` 的投影**，手工增删改入口收掉，只保留登录态与角色绑定 |
| `dept` | 直接复用 | **`SysDept` 成为 `SyncOrgUnit` 的投影**，组织架构管理界面收掉，只读 |
| `role` / `permission` | 直接复用 | **不变**——4 类角色与功能权限仍由本系统维护 |
| `auth` | 直接复用 | **不变**——SSO 用工号 / 学号对接 `SyncPerson` |
| 审计 / 外壳 / 分页 / 软删除 | 沿用 | **不变** |

## 3. 三条工作流（状态机）

### 3.1 入驻审核

```text
草稿 → 已提交 → 二级学院审核中 →【通过】→ 双创学院审核中 →【通过】→ 已生效
                    ↓【不通过】                  ↓【不通过】
                  退回修改 ←────────────────────────┘
```

⚠️ §3.1 说「信息修改需经双创学院审核生效」，§5.1 说二级学院审「信息修改申请」——**两级还是一级有冲突**（歧义 #5）。

### 3.2 预约指导（最长的一条）

```text
待导师确认 →【确认】已确认 → 指导中 → 记录已提交 → 学生已确认 → 已评价 → 已完成
     ↓【拒绝】已拒绝（带原因，可重新发起）
     ↓【调整时间】→ 回到待确认？
     ↓【学生异议】→ 复核中 → 管理员裁决
```

⚠️ 需求只给了 4 个状态（待确认 / 已确认 / 已拒绝 / 已完成），但 §2.4 异议、§3.4 记录填报、§2.5 评价都插在中间——**状态机需要补**（歧义 #2、#3）。

### 3.3 考核

```text
待初评 → 二级学院初评（等级 + 意见）→ 双创学院终评 →【通过】生效归档
                                          ↓【不通过】退回重评
                        导师可申诉 → 处理
```

## 4. 分期建议

### P0 · 地基（≈6 任务）

**做什么**：新工程落地（从 general-back 起）；**同步框架**（拉取 + 落表 + `SyncRun` 失败可见）；数据权限（学院级）；本地文件存储抽象；业务表建模迁移。
**验收**：一次同步跑通并能在 `SyncRun` 里看到失败明细；一个带学院级数据权限的查询跑通；一个文件能传能取。
**不做什么**：组织架构管理界面、账号管理界面（都归同步）。

### P1 · 导师专业档案 + 入驻审核（≈9 任务）

**覆盖**：§3.1、§4.3、§4.4、§5.1、§6.1（数据修改）、§6.4（**仅专业档案补录**）
**产出**：导师专业档案 CRUD、两级审核流、佐证材料上传下载预览
**不做**：导师账号批量导入（归同步）
**验收**：校内 / 校外导师能填专业档案，走完两级审核并生效。
**为什么先做**：没有导师档案，预约 / 评价 / 考核全部无从谈起。

### P2 · 预约指导主流程（≈14 任务）

**覆盖**：§2.1、§2.2、§2.3、§2.4、§3.2、§3.3、§3.4、§3.5

## 5. 剩余待定

### 5.1 先做哪一期？

建议 **P1**（导师专业档案 + 入驻审核）——三条主线的公共前提，独立可验收。
若想先看见「学生能搜到导师」，可做 P1 + P2 的检索部分。

### 5.2 新项目的落地方式

在 general-back 之上拓展，但另建仓库。两种做法：

| 选项 | 含义 | 代价 |
| --- | --- | --- |
| **a. 拷贝脚手架** | 把 general-back 复制成新工程，业务模块写在新工程里 | 立刻开工；但 general-back 后续改进不自动流入 |
| b. general-back 抽成依赖包 | 新工程 `npm i general-back`，业务模块写在新工程 | 职责干净；但要先做一次抽包重构（≈3–5 任务） |

建议 **a**：校内项目迭代快，抽包的收益要到「第二个业务系统」才兑现。

### 5.3 其余默认值（不阻塞开工）

- 跨系统互通（§6.7）：P5 再做，先 mock
- 提醒（§4.5）：P5，先站内消息，渠道留扩展点
- 考核权重（§6.6）：P3 先写死公式，P5 上配置界面

## 7. 本地文件存储的实现要点（D4 已定）

- 上传根目录走配置（`.env`），**不硬编码**
- 磁盘文件名用 **UUID**，原名只存 `FileObject` 元数据——避免冲突，也避免路径穿越
- 白名单限制类型（图片 / PDF）与单文件大小、单次数量（歧义 #11 待定）
- PDF 在线预览：响应头 `Content-Disposition: inline`；下载用 `attachment`
- **运维要求**：本地盘必须有备份策略，否则 §6.5「归档材料长期保存」落不了地
