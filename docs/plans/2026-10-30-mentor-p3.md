## P3 的裁决（**全部可推翻**，改一处即可）

| # | 歧义 | 裁决 | 理由 | 推翻代价 |
| ---: | --- | --- | --- | --- |
| **R41** | 三维度评分之外要不要存总分 | **存**：`StudentReview.overallScore DECIMAL(3,2)`，写入时算 `round((attitude + expertise + effect) / 3, 2)` | §6.3 要按均分统计。存下来才能用 Prisma 的 `aggregate` 求均值；现算要 `(a+b+c)/3` 的表达式，Prisma 表达不了，只能走裸 SQL，撞 R78 | 去掉该列，统计改用应用层汇总（分页失效，全校量级会爆内存） |
| **R42** | 文字评价必填吗 | **可空**，≤1000 字 | §2.5 只说「支持评分 + 文字评价」，没说必填；强制写文字会让评价率崩塌 | 改 DTO 一处 |
| **R43** | 评价在哪个状态可写 | **只在 `4 STUDENT_CONFIRMED`**。写入与 `4 → 6` 同一事务，`updateMany({where:{id,status:4}})` 的 `count === 0` → 409 / 34003 | P2 的 Task 32 已钉「评价接在 4 之后」；`6` 若由超时扫描进入（R52），评价窗口就该关了 | 放宽到 `{4,6}` 一处 |
| **R44** | 评价接口是否匿名 | **匿名**：`ReviewResponseDto` **不含**学生 ID / 姓名 / 学号 | 评价要给导师看、给学院看、给检索页展示。带学生身份等于把差评实名化，真实评价率会归零；追溯需求走数据库而非 API | 加字段一处，但**已发出的数据无法追回** |
| **R45** | 成果谁登记 | **导师本人登记，登记即生效**，管理员可改（§6.1 已具备） | §5.4「成果关联归档」在 P4，本期只需给 §5.2 的初评提供输入。加一道审核会凭空多一个状态机 | 加 `status` 列 + 审核路由 |
| **R46** | 成果的「级别」枚举 | `1 国家级 / 2 省级 / 3 市级 / 4 校级 / 5 院级`，**项目立项同用此标尺**（立项级别） | §5.2 只列「竞赛获奖、项目立项等」，没给级别表。两套标尺会让「按级别统计」分裂 | 改枚举 + 迁移 |
| **R47** | 考核「周期」的形态 | `Assessment.period VARCHAR(20)`，**只接受 `^\d{4}$`**（年度），区间固定为 `[YYYY-01-01 00:00:00, (YYYY+1)-01-01 00:00:00)`（服务器本地时区） | §6.6 的「按学期 / 年度」说的是**更新评分规则**，不是考核周期本身。学期边界由校历决定，代码里推断不出——硬编码一个学期区间就是在编校历 | 放开正则 + 改区间函数一处 |
| **R48** | 三个权重之和不为 1 怎么办 | 三个值都必须 **≥ 0**，且**和 > 0**；和为 1 直接用，否则**按比例归一化**，并把**实际使用值**回显在响应里 | 直接报错会让一次误配把整个考核卡死；静默归一化会让偏差不可见。回显是两者的折中 | 改为校验失败 409 一处 |
| **R49** | 工作量 / 成果怎么折算成百分制 | `reviewScore = round(reviewAvg × 20, 2)`；`workloadScore = min(100, round(guidanceCount × 100 / workloadTargetCount, 2))`；`achievementScore = min(100, round(achievementCount × 100 / achievementTargetCount, 2))`；`compositeScore = round(reviewScore×w1 + workloadScore×w2 + achievementScore×w3, 2)`。`workloadTargetCount` 默认 **10**、`achievementTargetCount` 默认 **5**，均为 `SysConfig` 键 | 需求只给了「依据哪些指标」，没给公式。没有公式就无法出可测的 `compositeScore`。目标值做成配置，口径变了不用改代码 | 改 3 个常量 / 2 个配置键 |
| **R50** | 初评等级由分数自动推导吗 | **不自动**。`collegeGrade` 由学院管理员**手工填**；`compositeScore` 只是参考值 | §5.2 原文是「填写初评意见、初评等级」——是人填的。自动推导会把「不合格」变成机器判的，学院无法解释 | 加一条推导规则 |
| **R51** | 申诉谁处理 | **双创学院**（`assessment:appeal-handle`） | 申诉针对的是终评结果（§3.8「对考核结果有异议」），终评方就是双创学院；退回二级学院等于让被申诉方自审 | 改权限码绑定一处 |
| **R52** | `4 STUDENT_CONFIRMED` 一直不评价会怎样 | **超期扫描**：`status=4` 且 `updatedAt < now − appointment.review_ttl_days`（默认 **30** 天）→ `6 COMPLETED` | 不扫的话大量预约永久停在 4，§5.3 的「指导完成率」和 §5.2 的工作量全部失真 | 去掉一个扫描分支；代价是统计口径要改 |
| **R53** | 初评要不要「草稿 → 提交」两跳 | **不要**。一条 `POST /assessments/:id/college-review`，`0|3 → 1` 一步到位 | 草稿态没人清理，且学院在 `GET` 里已经能看到实时指标，想清楚再提交即可。少一个状态、少一条路由 | 加 `collegeDraft` 分支 |
| **R54** | 终评等级能不能不同于初评等级 | **能**，`finalGrade` 独立于 `collegeGrade` | §6.2「结合全校指导成果、导师综合表现终评」——终评不是复核初评的分数，是重新定级 | 改一处写入 |
| **R55** | 考核指标什么时候冻结 | **提交初评时**把 6 个指标 + `compositeScore` + `weights` 冻结落库；`status=0` 时 `GET` 返回**实时试算**，`status≥1` 返回**冻结值** | 不冻结的话，初评之后学生再写评价会让「已提交的初评」数字自己变，审核链条失去可复核性 | 去掉冻结，永远实时算 |
| **R56** | 申诉「受理」会不会改分 | **不会**。受理只表示双创学院已收到并会复核，`Assessment` 不动 | 让受理触发改分就是第二个状态机，且需求 §3.8 只说「提交申诉说明」 | 加一条重评路由 |
| **R57** | 各域的 `self` 数据范围怎么译 | 沿用 **P1 的身份链** `SysUser.username → SyncPerson.login → SyncPerson.id`：`achievement` / `assessment` 的 self = `mentor_profile.person_id = 上一步 id`；`review` 的学生 self = `appointment.student_person_id = 上一步 id`；导师视角 = `appointment.mentor_profile_id ∈ 我的档案` | P1 已建立并复用了这条链（`mentor.service.ts` 文件头），不另造 | 改各 repository 一处 |
| **R58** | 指导时长从哪来 | **新增 `GuidanceRecord.durationMinutes INT UNSIGNED NOT NULL DEFAULT 0`**，P2 的记录提交 DTO **增加可选 `durationMinutes`（1–600）**，缺省 0 | §5.2 要「时长」，但 P2 的记录只有 `actualTime`（时刻），没有时长。没有这一列，时长统计只能瞎编 | 去掉该列，§5.2 的时长项退回「不统计」 |
| **R59** | 评价 / 成果 / 考核的权限码怎么切 | 9 个新码，见下表 | 与 P1/P2 的「一码一动作族」一致 | 合并若干码 |

## 考核状态机（`Assessment.status`）

| 值 | 名称 | 含义 | 进入条件 |
| ---: | --- | --- | --- |
| 0 | `DRAFT` | 待初评 | 学院创建 |
| 1 | `COLLEGE_SUBMITTED` | 待终评 | 学院提交初评（`0 → 1` / `3 → 1`） |
| 2 | `APPROVED` | 已生效 | 双创学院通过（`1 → 2`） |
| 3 | `RETURNED` | 已退回 | 双创学院退回（`1 → 3`） |

**迁移表（合法迁移只有这 4 条）**

```
0 DRAFT              → 1 COLLEGE_SUBMITTED   学院提交初评
1 COLLEGE_SUBMITTED  → 2 APPROVED            双创学院通过（终评等级可不同于初评）
1 COLLEGE_SUBMITTED  → 3 RETURNED            双创学院退回（意见必填）
3 RETURNED           → 1 COLLEGE_SUBMITTED   学院重评后再提交
```

**终态**：`2 APPROVED`。`3 RETURNED` 不是终态（可再提交）。
**同一导师同一 `period` 只有一条考核**（唯一约束走生成列，见 Task 37）。

## 申诉状态机（`AssessmentAppeal.status`）

| 值 | 名称 | 含义 | 进入条件 |
| ---: | --- | --- | --- |
| 0 | `PENDING` | 待处理 | 导师提交 |
| 1 | `ACCEPTED` | 已受理 | 双创学院受理 |
| 2 | `REJECTED` | 已驳回 | 双创学院驳回 |

**迁移**：`0 → 1`、`0 → 2`。**终态**：1 / 2。
**同一考核同时只许一条 `PENDING` 申诉**（服务层检查，第二个 → 409 / 35005）。
**申诉不改 `Assessment`**（R56）。

### Task 34: 学生评价接口 + `4 → 6` + 超期扫描

**Files:**
- Create: `src/modules/review/{review.module.ts,review.controller.ts,review.service.ts,review.repository.ts}`
- Create: `src/modules/review/dto/{create-review.dto.ts,review-response.dto.ts,list-review-query.dto.ts}`
- Modify: `src/modules/appointment/appointment.service.ts`（超期扫描加 `4 → 6` 分支）
- **不动** `src/config/*`：`appointment.review_ttl_days` 与 P2 的 `pending_ttl_hours` 一样是
  `SysConfig` 的键，运行时读库，不是环境变量（R17 已定）

**路由**

| 方法 | 路径 | 权限码 | 范围 |
| --- | --- | --- | --- |
| POST | `/appointments/:id/review` | `review:create` | `self` |
| GET | `/appointments/:id/review` | `review:list` | 学生本人 / 该预约导师 / 管理员 |
| GET | `/mentors/:mentorId/reviews` | `review:list` | 全角色（R44 匿名） |

**`POST` 语义**
- body：`{ attitude: 1-5, expertise: 1-5, effect: 1-5, comment?: string(≤1000) }`
- 只有该预约的**学生本人**可写（`appointment.studentPersonId` 的身份链，R57）；否则 **403 / 32002**
- 同一预约已有未删评价 → **409 / 34002**
- 预约 `status ≠ 4` → **409 / 34003**（R43）

> **顺序已改（P3 台账 R50）**：「已有评价」在「状态」**之前**。写评价与 `4 → 6` 同事务，
> 评价过的预约状态必然是 `6`——状态优先的话 34002 永远不可达，两个码里一个是死的。
> 并发下输的一方仍由事务里的 `count === 0` 兜到 34003。
- 成功：**同一事务内**插评价 + `updateMany({where:{id, status:4}, data:{status:6}})`；
  `count === 0` → 回滚 + **409 / 34003**（并发下另一个请求已经推进了）
- 返回 `201` + `ReviewResponseDto`

**`ReviewResponseDto`（R44：无任何学生身份字段）**

`id` / `appointmentId` / `mentorProfileId` / `attitude` / `expertise` / `effect` /
`overallScore` / `comment` / `createdAt`

**`GET /mentors/:mentorId/reviews` 响应**

`{ items: ReviewResponseDto[], total, page, pageSize, summary: { count, avg, attitudeAvg, expertiseAvg, effectAvg } }`

- `avg` 等一律 **2 位小数**，无评价时 `count = 0`、四个均值 `null`（**不是 0**——0 分和「没人评」不是一回事）
- `mentorId` 不存在 / 未生效 → **404 / 31102**

**`GET /appointments/:id/review`**
- 预约不存在 → 404 / 32001；不可见 → 403 / 32002
- 还没评价 → **404 / 34001**

  ```ts
  }

  ```
  Task 39（提交初评时冻结）、Task 41（`status = 0` 时实时试算）都调它。

**指标定义（全部按 `period` 的区间 `[YYYY-01-01, (YYYY+1)-01-01)` 过滤，R47）**

| 字段 | 口径 |
| --- | --- |
| `reviewCount` | `StudentReview` 未删，其 `appointment.mentorProfileId = mentorId`，`StudentReview.createdAt ∈ 区间` |

| `achievementCount` | `Achievement` 未删，`mentorId = mentorId`，`awardedAt ∈ 区间` |

**打分（R49）**

- `reviewScore = reviewAvg === null ? 0 : round(reviewAvg × 20, 2)`
- `workloadScore = min(100, round(guidanceCount × 100 / workloadTargetCount, 2))`；目标值 ≤ 0 时按 **1** 处理
- `achievementScore = min(100, round(achievementCount × 100 / achievementTargetCount, 2))`；同上
- `compositeScore = round(reviewScore×w.review + workloadScore×w.workload + achievementScore×w.achievement, 2)`

**判据**

- [ ] `guidanceCount = 25`、目标 10 → `workloadScore = 100`（封顶）
- [ ] `workloadTargetCount = 0` → 不除零，按 1 处理
- [ ] `studentCount` 是去重数：同一学生 3 次指导 → `studentCount = 1`
- [ ] 区间边界：`awardedAt = YYYY-01-01` 计入，`= (YYYY+1)-01-01` 不计入（半开区间）
