| **R29** | `keyword` 要不要匹配 `researchFields` | **不匹配**。方向检索走 `researchField` 的 `array_contains` 精确筛选 | JSON 数组的**模糊**匹配在 Prisma 里只能靠 `path: '$[i]'` 按下标展开，上限是一个手写常量；超出部分**静默搜不到、不报错**，且与 `researchField` 的口径（任意下标都命中）不一致。需求 §2.1 本来就把「研究领域 / 指导方向」列为**筛选条件**而非关键词 | 加回模糊匹配需先解决「任意下标模糊」的查询方式（派生文本列或 `JSON_SEARCH`，后者受 R78 裸 SQL 约束） |
| **R30** | `requestedTime` 能不能填过去的时间 | **不能**：必须晚于当前时间，否则 **400 / 10001** | 需求只说「期望指导时间」，但填过去的时间是无意义输入；放行会让状态机里出现「已过期还待确认」的脏态，而超时扫描只处理 `PENDING`，这类脏数据永远清不掉 | 去掉校验一处；代价是脏态只能靠人工清理 |
| **R31** | 时段 `weekday` / `startTime` / `endTime` 是**哪个时区**的墙钟时间 | **本地时区**，默认 `Asia/Shanghai`，由 `APP_TIMEZONE` 覆盖。`requestedTime` 是 UTC 时刻，比较前先转成该时区 | 时段是**每周重复的墙钟时间**，本身不带时区；`DATETIME(3)` 存 UTC 是**时刻**的口径，两者不是一回事。按 UTC 比较的话，导师开「周一 09:00-11:00」在学生眼里是北京时间 17:00——对国内高校是明确错的 | 改成 UTC 口径只需改 `matchesSlot` 一处 + 默认配置值 |
| **R32** | 并发去重的行锁锁哪一行 | **锁导师档案行** `SELECT id FROM mentor_profile WHERE id = ? FOR UPDATE` | 锁时段行时，**两个不同时段**的请求互不阻塞，双方都读到「该学生对导师在途数 = 0」→ 同一学生对同一导师出现 2 条在途，守卫 ⑥ 形同虚设。锁导师行**一把锁同时覆盖守卫 ⑤ 和 ⑥**；加第二把锁会引入 A→B / B→A 的**死锁**风险。锁业务层 `mentor_profile`，不碰同步层 `sync_person` | 改回锁时段行只需改一句，代价是守卫 ⑥ 并发下失效 |
| **R33** | `reschedule` 的 `proposedTime` 要不要校验导师开放时段 | **不校验时段，只校验「必须是未来时间」** | 导师临时安排时不该被自己的周表卡住；需求 §3.2 本就允许「临时修改、关闭时段」。校验时段会让「本周临时加一次」变成必须先改周表 | 加校验一处；代价是导师每次临时安排都要先补时段 |
| **R34** | `appointment.pending_ttl_hours` 配成负数怎么办 | **读出来先 `Math.max(0, ttlHours)`**。`0` 保持原语义（cutoff = now）；负数一律当 `0` | `SysConfig` 层不校验正负；配成 `-1` 时 `cutoff = now + 1h` 落到**未来**，会把**刚创建的 `PENDING`** 扫成 `9 EXPIRED`，而 `9` 是终态不可逆、且只有 info 日志无告警 | 去掉 clamp 一处；代价是一次配置误配烧掉所有新预约 |
| **R35** | `actualTime`（实际指导时间）能不能填未来 | **不能**：必须不晚于当前时间，否则 **400 / 10001** | 它是「已经发生的事」；填未来时间会让考核统计把未发生的指导算进去 | 去掉校验一处 |
| **R36** | `disputeReason` 表示历史还是「当前未决异议」 | **当前未决异议**。`3 → 4`（学生确认）置 `null`；`5 → 3`（管理员退回）**保留** | 不清的话，「异议 → 退回 → 学生再确认」会留下 `status=4` 且 `disputeReason` 非 null 的脏态 | 改一处更新即可；历史留痕是 P3/P4 的事 |
| **R37** | `5 DISPUTED → 3 RECORD_SUBMITTED` 的「退回重填」怎么填 | **`POST /appointments/:id/record` 在 `status = 3` 时也放行**（仅导师本人）：`1` 建记录并 `1→3`；`3` **更新已有记录、状态保持 3** | 不放开的话「重填」无路可走——记录有唯一键、没有编辑接口、`record` 守卫只认 `status=1`，`5→3` 之后导师改不了任何东西，那句话就是空话 | 若坚持「退回即终局」，把 `5 → 3` 改掉，改一处迁移表 |
| **R38** | R12 表里的 `1 CONFIRMED → 9 EXPIRED` 要不要实现 | **要实现**。扫描 `status = 1` 且 **`requestedTime`** 早于「现在 − `appointment.confirmed_grace_hours`（默认 24）」→ `9` | **本计划原先自相矛盾**：R12 的状态机表列了 `1 → 9`，而 Task 25 一节写「只扫 `PENDING`」。不补的话，已确认但没发生的预约永远停在 `1`——导师可以无限期后补记录，`actualTime` 是久远的过去，等于把没发生的事写成发生了。**基准是 `requestedTime` 不是 `createdAt`** | 去掉这条扫描一处；代价是脏态只能人工清理 |

## 预约状态机（R12，**P3 依赖它，先定死**）

| 值 | 枚举名 | 含义 | 谁推进 |
| ---: | --- | --- | --- |
| 0 | `PENDING` | 待导师确认 | 学生发起 |
| 1 | `CONFIRMED` | 已确认 | 导师确认 |
| 2 | `IN_PROGRESS` | 指导中 | 到达确认时间后导师开始（或自动） |
| 3 | `RECORD_SUBMITTED` | 记录已提交 | 导师填完记录 |
| 4 | `STUDENT_CONFIRMED` | 学生已确认记录 | 学生确认 |
| 5 | `DISPUTED` | 学生异议，复核中 | 学生提异议 |
| 6 | `COMPLETED` | 已完成 | 学生确认 / 管理员裁决通过 |
| 7 | `REJECTED` | 导师已拒绝（带原因） | 导师拒绝 |
| 8 | `CANCELLED` | 学生已取消 | 学生取消 |
| 9 | `EXPIRED` | 超时未处理 | 定时任务 |

**合法迁移表**（其余一律 **409 / 32003**）：

```
0 PENDING     → 1 CONFIRMED | 7 REJECTED | 8 CANCELLED | 9 EXPIRED
                （导师「调整时间」= 留在 0，只改 proposedTime）
1 CONFIRMED   → 2 IN_PROGRESS | 8 CANCELLED | 9 EXPIRED
2 IN_PROGRESS → 3 RECORD_SUBMITTED
3 RECORD_SUBMITTED → 4 STUDENT_CONFIRMED | 5 DISPUTED
4 STUDENT_CONFIRMED → 6 COMPLETED        （P3 评价接在 4 之后）
5 DISPUTED    → 6 COMPLETED | 3 RECORD_SUBMITTED   （管理员裁决：通过 / 退回重填）
```

**终态**：`6 COMPLETED` / `7 REJECTED` / `8 CANCELLED` / `9 EXPIRED`——终态不再迁移。
